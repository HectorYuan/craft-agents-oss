### 本版主题：把「CI 里不可复现的门禁」修好 ⇒ 三平台交付能力恢复

★ 本版的起因不是功能需求，而是**一道门禁在 CI 里恒红**：v0.9.20 的 CI（run `40894104769`）
10 个 job 里红了 4 个，而**代码本身没问题**（其余 job 全绿，`14141 passed / 1 failed`，
唯一失败用例是「在真实检出根目录上断言门禁通过」那条 ⇒ 它复现的正是门禁自己的缺陷）。
⇒ 门禁在 CI 里恒红 ⇒ **tag 的 sha 永远拿不到 CI 绿证据** ⇒ 发布门禁 `gate-ci` 永不放行
⇒ **Windows `.exe` 与 Linux 三件套结构性产不出**（与「构建机是否在线」无关）。

#### 新增

- **修炼域「五层回路」母题签名图形 + 回合状态徽章**（vendor 侧随版本一同交付）。
- **墓碑回收** `zenskill sync prune`：删除标记不回收 ⇒ 账本无界增长；本命令按保留期回收墓碑
  （判定「已删除」看的是「远端有没有这条」，不是「远端有没有墓碑」⇒ 回收不丢语义）。
- **Windows 与 Linux 产物恢复交付**：本版起 Windows `.exe` / Linux `.deb` / `.AppImage` / wheel
  与 macOS `.dmg` / `.zip` **同版齐发**（前提：该 sha 的 CI 为绿 —— 本版已把这道门禁修到可复现）。

#### 修复

- **看板不再渲染易变读数**（D-11）：看板原会把「最新 tag=vX.Y.Z（共 N 个）」「子模块当前分支 /
  是否 detached」这类**不随提交变**的量抄进去，而看板是**逐字节比对**的 ⇒ **每推一次 tag 就红**。
  ⇒ 看板改为只给**结论 + 判据名**，明细与易变读数只进 CLI。
- **CI 检出补拉 tag**：协作状态门禁要读本地 tag 列表，而 CI 原用 `fetch-depth: 1`（不拉 tag）
  ⇒ 检出里 0 个 tag ⇒ strict 的 `tag_exists` 必判红 ⇒ **本地全绿、CI 必红**。
  ⇒ 门禁相关 job 改为把 tag 拉下来，让判据判在**真实读数**上。
- **清掉一处合并残留**：已发布的 v0.9.20 台账里残留一行 diff3 冲突基准标记
  （手解冲突时漏删 base 段头）⇒ 现有门禁无一条扫冲突标记 ⇒ 已登记为 **D-12**（待补门禁）。

#### 工程与发版链

- 协作状态门禁（G-COORD）**在 CI 里重新可复现** ⇒ 绿证据重新可得 ⇒ 发布门禁不再被自身堵死。
- `vendor-tests` 去掉 electron 二进制下载这条网络依赖。
- 看板把「已释放」的认领显示成「已认领」的显示缺陷修正。

#### 已知限制

- 本版无已知交付限制（Windows `.exe` / Linux 三件套 / macOS `.dmg` / `.zip` 同版齐发）。

#### 本版承接自 v0.9.20 的三笔债（在此一并交代）

- **「v0.9.20 的绿是偶然的」这一笔已还**：协作状态门禁曾因「CI 检出无 tag」与「看板抄了易变读数」
  而在 CI 里恒红（本地却全绿）⇒ 已根治：读数型基准不再渲染进看板、`tag_exists` 降为
  advisory（环境读数不为它判红）、CI 显式拉取真实 tag 集合 ⇒ **换一台干净 runner 也绿**。
- **「v0.9.20 的更新日志没写墓碑回收」这一笔已还**：本版更新日志含 `zenskill sync prune`。
- **「v0.9.20 同版本号下 macOS 字节已变」这一笔无法还**（已发布即不可变）⇒ 显式登记：
  重指 tag 后 macOS 资产被重建覆盖，已下载过 v0.9.20 macOS 包的用户拿到的字节与现在不同。
