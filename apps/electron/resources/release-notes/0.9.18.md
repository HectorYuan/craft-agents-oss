### 发版链路修复：Windows 产物第一次能真出来（含四处判据级缺陷）

★ 本版**首次带 Windows NSIS 安装包**（v0.9.16 / v0.9.17 都缺）⇒ 查下去发现
**四个互相独立的缺陷叠在一起**，每一个单独看都像「环境问题」：

1. **门禁死锁（最严重）**：`scripts/ci/gate-check.sh` 数 **check-runs** 且要求
   `total >= 6` ⇒ 一个「**从未启动就被取消**」的 CI run **一个 check-run 都不产生**
   ⇒ 排除 Release 自己的 check-run 后集合**为空** ⇒ 门禁把「CI 已被取消」误判成
   「CI 还没跑完」⇒ **死等 40 分钟**，期间**一直占着唯一的 linux runner**
   ⇒ 把后续所有 CI 全部堵死（2026-10-26 实测）。
   ⇒ 改为按「**名为 CI 的 workflow run** 的 `status`/`conclusion`」判四态
   （绿 / 红 / 等 / 无）；另修「**短 SHA 会被 API 静默忽略过滤**」⇒ 强制全长 40 位。
2. **detect-win 三态是死代码**：注释承诺三态（探测到在线 / 探测到 0 个 / 探测失败），
   **代码里却只有一处 `echo "local=true"`** ⇒ 恒为 true ⇒ `windows-hosted` 是
   **永远走不到的死代码**。⇒ 三态真正落地。
3. **「探测失败」被当成「探测到 0」**：注册计数用 `0` 初始化 ⇒ 而本仓
   `RUNNERS_READ_PAT` 未设置 ⇒ 探测必然 403 ⇒ 计数恒 0 ⇒ 被误判成「真的没注册」
   ⇒ 腿被 skip ⇒ **Windows 产物静默出不来**。⇒ 计数改**空值初始化**，
   失败走**乐观**分支（排队等它上线）。
4. **Windows 腿的 `checkout` 必挂（真因）**：2026-10-16/17 两次发版的 Windows 腿是
   **`failure`（不是 skipped）** ⇒ 它**真的被 runner 接了活**，红在
   **`Run actions/checkout@v4`**（NSIS 那步根本没跑到）⇒ ① 仓库属 hecto 而 runner
   服务以 `NETWORK SERVICE` 身份运行 ⇒ git "detected dubious ownership" ⇒
   **在输出任何东西之前**就死；② runner 的 git exec-path 缺 `git-submodule`
   （mac 腿 2026-10-25 踩过同一类坑）。⇒ **Windows 腿补「git 自举」步**
   （`safe.directory` + 前置可用 git + **自证** `submodule --help` 可用）。

注册计数**必须空值初始化**、Windows 腿**必须有 git 自举步**且该步含

⇒ **判据必须落在真实执行体上，名字与注释只能当线索，不能当证据**。

### 优化清单收口：B1 / B11 / B13 / B14 + energy 落盘改 JSONL

本批的共同主题：**把「靠自觉」的东西变成「可执行的门禁」**，并把**会漂移的数字变成可复算的命令**。

- **B1 · async 内同步文件 I/O 全量清零（41 → 0）**
  修法统一为「抽出**嵌套同步 helper** + `await asyncio.to_thread(helper, ...)`」
  （嵌套同步函数体不计入扫描范围，这是修法能成立的关键）。
  **判据口径同步修正（三处，只收紧不放宽）**：
  ① `str.replace`（≥2 个位置实参）是**纯内存字符串操作**、不是文件 I/O
  ⇒ 原先两处误报消除（真实基线 39），扫描器 `--self-test` 补第 4 类负控；
  ② 但 `os.replace(a, b)` **同为 2 个实参**却是真 I/O（原子改名）⇒ 补「接收者是
  模块引用 ⇒ 不豁免」+ 对应负控（否则是**假阴性**）；
  ③ `Path.resolve()` 走 realpath(3) ⇒ **真的碰文件系统**，此前不在口径内
  ⇒ 纳入 `IO_NAMES` 并补正控，随之整改 3 处命中（CHANGELOG 路径提升为模块级
  常量；路径穿越判定整段挪进同步 helper + `to_thread`）。
  CI 预算 `--max 41` → **`--max 0`**（零容忍）。
- **B11 · 裸吞异常全量清零（360 → 0）**
  判定口径：`except` 体**只有** `pass`/`continue`。
  ⇒ **单纯窄化异常类型并不会让命中消失**，真正让命中消失的是
  **写出理由**（`# swallow: 原因`，必须写在 **`except` 关键字那一行**）或**加一条日志**
  （使 except 体不再只有 pass/continue）。
  三类处理并用：窄化+理由 / 保留 catch-all + `logger.exception`（模块无 logger 则新建
  模块级 logger + `logger.warning(..., exc_info=True)`）/ 仅补理由。
  豁免清单**保持不存在**（零豁免）；CI 由 **`--warn` 改硬门禁**。
- **B13 · 可执行错误文案规范（状态码 + 厂商原文 + 下一步动作）**
  新增 `zenskill/core/actionable_error.py`（零包内依赖）：统一构造/渲染/解析，
  既给**人读**的一行文本，也给**机器读**的结构化 dict（⇒ CLI/GUI/MCP 同源渲染，
  杜绝「同一端点、不同 CLI、不同粒度」）。
  落地到三个错误出口：provider HTTP 重试层 / 线上模型目录拉取 / 连接探活。
  兼容既有解析：`is_permanent_http_error` 同时认旧形态 `HTTP <code>:`
  与新形态 `HTTP <code> @ <端点>：`；`should_degrade_tools` 的厂商原文抽取改走共享解析器。
  新增门禁 `scripts/check_actionable_errors.py`（规范面 12 个状态码 + 接线面「登记的出口
  必须**真的 import 并调用**共享模块」，AST 判据）与三类负控自检，已挂 CI。
  ⚠️ **门禁脚本必须零包内依赖**：CI 的质量 job 用**裸 `python3`**（不装依赖）跑门禁，
  `import zenskill...` 会触发 `zenskill/__init__.py` 的重依赖链（packaging / aiohttp）
  ⇒ 裸 python3 上直接 ImportError ⇒ **CI 变红**。
  ⇒ 共享规范模块按**文件路径**加载；「真跑三个出口」的**行为面**移到 pytest
  （`tests/test_actionable_errors.py`，32 条）—— 那里才有完整依赖环境。
  ⚠️ 接线面判据由「查子串」升级为 **AST 判据** —— 旧判据下**只在注释里提一句**
  `actionable_error` 也能过 ⇒ 门禁无牙；现要求 AST 里有指向该模块的 import
  **且**被 import 的符号**被调用**（负控含「只注释」「只 import 不调用」两类样本）。
- **B14 · roadmap_v3 数字与实况脱节**
  `docs/roadmap_v3.md` §三/§四 改为「**能力 + 验证门禁**」表达：

- **energy 落盘改追加式 JSONL（写放大实测降 32.6 倍）**
  由整文档 `energy.json` 改为追加式 `energy.jsonl`（`k=st` 状态快照行 + `k=ev` 事件行，
  对齐 `actions.jsonl` 既有约定）：写路径**只追加**（≈270B/次）而非整份重写（≈12KB/次）；
  文件增长由**摊销压实**兜底（行数 > 250 或体积 > 256KB 时，
  重写为「1 条最新状态 + 最近 100 条事件」；触发条件**无状态** ⇒ 跨进程也成立）。
  **同口径实测**（300 次 burn，总写入字节数）：旧 **3477 KB** → 新 **107 KB** ⇒ **32.6 倍**。
  **向后兼容**：旧 `energy.json` 仍可读，且**迁移只发生在首次写入**（读路径不再写盘）。
  ⚠️ 但「已迁移后」它是一份**永不更新的旧快照** ⇒ 回退读它等于**把余额回滚到迁移
  那一刻** ⇒ 已迁移但数据损坏时**绝不回退**，改走默认池并留日志。
  **独立复核（只读审计）用探针复现了 5 条真实丢数据路径，全部修掉并补成守卫**：
  ① 损坏后回退陈旧旧文件（余额回滚）；② 有事件行无状态行 ⇒ 余额被重置为默认满值
  （⇒ 引入**全局事件序号**：状态行带「已计入条数」、事件行带「全局序号」，
  读路径把尾部未计入事件按增量叠加 ⇒ 最后一次操作不丢）；③ 写盘失败时事件被标记成
  「已落盘」而永久丢失、且调用方拿到「假的成功」（⇒ 写成功才推进计数、OSError 上抛）；
  ④ 压实在锁外 + tmp 名不唯一 ⇒ 并发追加被覆盖 ⇒ 静默丢事件（⇒ 压实移进**按文件
  路径共享的锁**、tmp 名 pid+uuid4 唯一）；⑤ 压实触发用「上次压实后的体积」当地板而
  该值只在进程内存里 ⇒ 每个新进程首次写都退化成全量重写（⇒ 触发条件改**无状态**）。

### EnergyEngine 写放大：读路径不再写盘

- **问题**：能量同步（境界 → 能量上限）挂在**读路径**上（`status` / `advise` / 构造器），
  而旧实现**无条件落盘** ⇒ 一次「读」被放大成两次元数据写（tmp 落盘 + rename）。后果：
  ① TUI 刷新 / MCP 工具 / CLI 每次读都在写盘；② `energy.json` 的 mtime 每次读都变
  （上层 `progression` 缓存被迫改用内容哈希绕开）；③ `recover()` 一次操作把同一份内容写两遍。
- **修复**：同步结果**没有变化时不再落盘**；有变化时**仍然落盘** ⇒ 持久性语义零变化
  （旧实现在「无变化」时写出的字节与上一次完全相同，跳过它对磁盘终态无影响）。
- **实测**（本地 mac/APFS）：1000 轮 burn+recover 落盘 **3000 → 2000 次**（-33%）、
  耗时 1.60s → 1.18s；200 次「构造 + status()」落盘 **400 → 0 次**、耗时 0.301s → 0.125s。
- **守卫**：`tests/test_gtd/test_energy_persistence.py`（10 条）钉住两侧 ——
  不该写时**一次都不写**、该写时**必须写**、计数口径固定
  （burn 1 次 / recover 1 次 / N 轮 2N 次）；**负控自证**：退回旧实现后 5 条转红
  （200 轮实测 600 次落盘）。
- **同族体检**：GTD 其余引擎（Action / Inbox / Calendar / Project / Incubating）
  读路径本就 0 写盘，energy 是包里唯一的患者，现已归零。
