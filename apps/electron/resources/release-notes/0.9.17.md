### 数据库持久性口径（B12）：默认 FULL，慢盘 CI 显式降级

- 统一连接层**显式声明** `PRAGMA synchronous`（此前只设 `journal_mode=WAL`
  ⇒ SQLite 取默认 FULL ⇒ 每次 commit 一次 fsync）
- **默认保持 FULL**（生产持久性语义零变化）；仅 CI 慢盘腿用
  `ZENSKILL_DB_SYNCHRONOUS=NORMAL` 显式降级（非法值回退 FULL 并告警）
- **治根**：3 个 GTD 性能用例（1000 次写）在慢盘 runner 上实测
  9.72s / 14.07s / 5.39s 撞 2.0s / 3.0s 阈值 ⇒ 降级后全部回到阈值内
  （**性能阈值一个都没动**，是治根不是放宽）
- 门禁 `scripts/check_db_synchronous.py`：统一层必须显式声明 + 默认必须 FULL
  + 裸 `sqlite3.connect()` 预算 ratchet，自带 3 类负控 + 正控

### CI 红灯治理：门禁强度提升（不是放宽）

- **并发策略** `cancel-in-progress: true → false`：原策略使一天内多轮 CI
  全部被并发 push 作废 ⇒ 门禁读数永远拿不到（实测修复生效）
- **新增/加固门禁**：吞异常（存量 360，告警模式待清零）、同步 I/O 预算 41、
  静态自由名（搬移/改名不许留悬空依赖）、数据库持久性口径、
  **版本四处一致**（新立）
- **版本一致性门禁**（新立）：pyproject / `__init__` / `__main__` /
  vendor electron `package.json` 必须一致 ⇒ 修掉一个历史漂移：electron 那处
  停在 0.9.14 ⇒ **v0.9.16 已发布产物的 GUI 版本号显示错误**（本版起修正）
- **vendor 子模块测试修复**：`pages/data-store` kv cap 用例的前置原为
  1000 次逐条 commit（每次 fsync）⇒ 改一次批量事务 ⇒ 慢盘 runner 上
  5~17s 撞 bun test 5s timeout 的偶发红灯治根
  （**被测的 cap 拒绝 + 回滚路径一条断言没少**）
